# ADR Draft Request — R10-S01: Canonical Extracted Document Contract

You are generating an Architecture Decision Record for the RAG Platform.

This ADR follows the existing ADR style already established in this repository.

Do not simply document an object model.

Instead, explain the architectural reasoning behind the decisions.

The tone should be suitable for a senior software engineering team and remain implementation-agnostic where appropriate.

---

## Background

The platform is entering Phase R10 (Text Extraction & Normalisation).

Multiple document extractors (TXT, PDF, DOCX initially, with future HTML, Markdown and other formats) will feed a common ingestion pipeline.

The remainder of the pipeline (normalisation, chunking, embedding, retrieval, indexing and citation generation) must not depend upon any individual document format or parser implementation.

This ADR defines the architectural contract that every extractor must produce.

---

## Core Architectural Principle

Include the following principle prominently within the ADR.

> Preserve as much semantic information as possible during extraction. Defer any lossy transformation until a later stage where there is sufficient context to make an informed decision.

Also include the following principle.

> Extraction is a loss-minimisation stage, not a simplification stage.
>
> The responsibility of extraction is to preserve the document's semantic structure as faithfully as practical. Decisions that intentionally discard information belong to later pipeline stages where there is sufficient context to evaluate the trade-offs.

Explain why this philosophy improves long-term maintainability, retrieval quality, future extensibility and downstream AI processing.

---

## Architectural Decisions

Record the following decisions.

### Canonical document contract

Every extractor shall produce a single canonical ExtractedDocument representation.

Downstream components must depend only upon this contract and never on parser-specific output.

---

### Separation of responsibilities

Extraction

- Reads source documents.
- Extracts content.
- Preserves semantic structure.
- Records provenance.

Normalisation

- Converts parser-specific output into the canonical representation.
- Performs structural normalisation only.
- Does not perform chunking.

Chunking

- Operates exclusively on the canonical representation.
- Must remain independent of document format.

Explain why each stage has a single responsibility.

---

### Canonical Element model

Describe the architectural decision to introduce a common Element abstraction.

The initial contract should support semantic element types including (at minimum):

- HeadingElement
- ParagraphElement
- ListElement
- TableElement
- CodeBlockElement
- QuoteElement
- HyperlinkElement
- ImageCaptionElement
- HorizontalRuleElement
- FootnoteElement

The contract must remain open for future element types without requiring downstream architectural changes.

Explain why this follows the Open/Closed Principle.

---

### Preserve semantic structure

State that extraction should preserve wherever practical:

- reading order
- document hierarchy
- headings
- paragraphs
- lists
- tables
- hyperlinks
- image captions
- source locations
- page numbering
- extraction confidence
- document metadata

Explain why preserving information is preferable to discarding information early.

Include the architectural observation:

> Information can always be discarded later.
> Information cannot be recreated later.

---

### Source provenance

Each semantic element should retain sufficient provenance information to support:

- citations
- debugging
- auditing
- replay
- future explainability

The ADR should discuss provenance as an architectural concern rather than defining exact fields.

---

### Stable identifiers

Every semantic element should possess a stable identifier (UUID or equivalent).

Explain why stable identifiers improve traceability, citations, debugging and future extensibility.

---

### Immutability

Record the decision that ExtractedDocument is immutable.

Once produced by a pipeline stage it must never be modified.

Subsequent pipeline stages create new derived representations rather than mutating previous ones.

Discuss the architectural benefits including:

- data integrity
- auditability
- replayability
- deterministic processing
- debugging
- security
- future event-driven processing

---

### Extraction failures

Differentiate between transient and permanent failures.

Permanent failures should include:

- machine-readable failure codes
- human-readable explanations suitable for end users

Explain that retrying permanent failures provides little value and that meaningful feedback enables corrective action.

State that all extraction failures must be audited.

---

### Confidence

Where supported by extractors, semantic elements may include extraction confidence.

Explain how confidence enables future quality controls without forcing immediate implementation.

---

### Future extensibility

Discuss why preserving semantic richness now enables future capabilities such as:

- improved chunking
- better retrieval
- richer citations
- OCR integration
- diagram extraction
- formula support
- document intelligence
- alternative chunking strategies

without requiring redesign of the extraction architecture.

---

## Consequences

Include both advantages and trade-offs.

Advantages should include:

- loose coupling
- extensibility
- maintainability
- better AI retrieval
- future-proof architecture
- improved observability
- replayability
- deterministic processing

Trade-offs should include:

- increased implementation complexity
- richer object model
- additional testing requirements
- slightly increased memory consumption

Explain why these trade-offs are acceptable given the long-term architectural benefits.
