# Phase 15

Phase 15 is now:

## Ingestion Orchestration

It exists because we discovered a genuine architectural seam after completing Vector Storage.

Phase 14 established:

- PostgreSQL is authoritative.
- Canonical chunk text is durably stored.
- Qdrant is a rebuildable search projection.
- VectorStore owns vector persistence.
- Workspace corpus generations.
- Embedding-space generations.
- Deterministic point identity.
- Completeness verification.

What Phase 14 deliberately did **not** decide is:

**How two independent services cooperate to produce an authoritative indexed document.**

That is Phase 15.

---

# What this ADR should answer

This ADR is **not** about callbacks.

It is about the authoritative contract between:

Laravel

↓

Python

↓

Laravel

It should define:

- service ownership;
- authoritative state transitions;
- processing contracts;
- completion contracts;
- failure contracts;
- idempotency;
- queue semantics;
- trust boundaries;
- distributed workflow.

The implementation mechanism (HTTP endpoints, etc.) exists only to satisfy that architecture.

# Questions to analyse

Please independently review and recommend the strongest architecture for:

## 1. Service ownership

Laravel currently owns:

- PostgreSQL
- Documents
- Lifecycle
- Chunks
- Generations

Python currently owns:

- extraction
- normalisation
- chunking
- embedding
- VectorStore
- Qdrant persistence
- vector completeness verification

Should this ownership change?

If not, explain why.

---

## 2. State transitions

Review the complete Document lifecycle.

Is:

UPLOADED

↓

QUEUED

↓

PROCESSING

↓

INDEXED

↓

FAILED

still sufficient?

Or should another explicit lifecycle state now exist between PROCESSING and INDEXED?

For example:

PROCESSING

↓

INDEXING

↓

INDEXED

or another equivalent concept.

I do **not** want another state added simply because we can.

Only recommend one if it materially improves correctness or clarity.

---

## 3. Worker-to-Laravel communication

Compare possible architectural approaches, including:

- authenticated HTTP callbacks;
- response queue;
- EventBridge/event bus;
- transactional outbox return;
- any other reasonable alternative.

Evaluate them against:

- simplicity;
- correctness;
- observability;
- idempotency;
- retries;
- operational complexity;
- consistency with the existing architecture.

Recommend one.

---

## 4. Trust boundaries

Exactly what is Laravel trusting?

Exactly what is Python asserting?

Exactly what must Laravel verify independently?

Exactly what can Laravel never independently prove?

For example:

Laravel owns canonical chunks.

Python owns Qdrant verification.

How should those responsibilities meet?

---

## 5. Completion semantics

Exactly what facts must exist before Laravel may honestly transition:

PROCESSING

↓

INDEXED

Should the completion contract contain:

- manifests;
- digests;
- counts;
- lineage;
- generation identities;
- embedding profile;
- verification evidence.

Recommend the strongest design.

---

## 6. Failure semantics

Distinguish:

- transient failures;
- permanent failures;
- callback failures;
- infrastructure failures;
- provider failures;
- validation failures.

Who owns classifying each?

Who owns deciding retry?

Who owns deciding FAILED?

---

## 7. Queue semantics

Review:

- acknowledgement timing;
- redelivery;
- duplicate delivery;
- DLQ behaviour;
- processing-attempt identity.

Recommend the cleanest end-to-end contract.

---

## 8. Initial provisioning

Phase 14 deliberately stopped short of deciding:

- first embedding-space generation;
- first workspace corpus generation;
- first activation.

Determine where those responsibilities belong.

---

## 9. Observability

Extend ADR-0012 naturally.

Determine:

- trace boundaries;
- correlation identifiers;
- authoritative completion events;
- safe telemetry.

---

## 10. Future-proofing

The architecture should naturally support:

- multiple workers;
- multiple embedding providers;
- future retrieval;
- reranking;
- evaluation;
- future document versioning.

Without implementing them now.
