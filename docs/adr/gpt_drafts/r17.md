----------------------------------------------------------------------
1. Core retrieval principle
----------------------------------------------------------------------

Retrieval answers:

“Which evidence is eligible to answer this authorised user’s question?”

It does not generate the answer.

The intended high-level flow is:

Authenticated user
→ Laravel resolves AuthorisedKnowledgeScope
→ Laravel calls Python RetrievalPlanner
→ Python returns typed RetrievalPlan
→ Laravel EligibilityResolver combines:
    - RetrievalPlan
    - AuthorisedKnowledgeScope
    - authoritative DocumentFamily/version/governance/temporal data from ADR-0017
→ Laravel produces EligibleRetrievalScope
→ Laravel synchronously calls Python Retriever
→ Python performs semantic retrieval only inside the resolved scope
→ Python returns RetrievalResult

Generation is a later phase.

----------------------------------------------------------------------
2. RetrievalPlanner
----------------------------------------------------------------------

Introduce a provider-neutral RetrievalPlanner boundary.

Input:

- natural-language question;
- authoritative evaluation time.

Output:

a strict, typed RetrievalPlan.

V1 modes:

- CURRENT
- VALID_AT_DATE
- COMPARE
- CLARIFICATION_REQUIRED

The production V1 planner is intentionally LLM-backed.

This is a settled design choice.

Do NOT replace the intended production planner with a keyword/regex/rule-based implementation.

The LLM is used only for the bounded semantic task:

natural language
→ typed retrieval intent

The planner must not:

- authorise;
- resolve document IDs;
- access PostgreSQL;
- access Qdrant;
- retrieve;
- embed;
- rerank;
- answer.

It should be provider-neutral, like Embedder / VectorStore / Reranker.

Around the LLM output, require:

- strict structured output;
- schema validation;
- deterministic date/selector validation;
- safe fallback behaviour;
- CLARIFICATION_REQUIRED rather than guessing unresolved historical/comparison intent;
- deterministic/fake planner implementation for tests;
- evaluation compatibility for later Stage 16.5.

A rule-based planner may exist as:
- a test double;
- fallback;
- baseline;
- evaluation comparator;

but is not the primary V1 production implementation.

----------------------------------------------------------------------
3. RetrievalPlan
----------------------------------------------------------------------

Define the minimum provider-neutral plan contract.

At minimum it must express:

CURRENT

VALID_AT_DATE
- explicit instant or bounded temporal selector

COMPARE
- two symbolic version anchors

CLARIFICATION_REQUIRED
- controlled reason / clarification requirement

For COMPARE, support the V1 symbolic anchors:

- CURRENT
- AT_DATE(date)
- PREVIOUS

The planner never resolves these to actual Document IDs.

Laravel resolves them later.

Avoid pretending LLM confidence values are calibrated probabilities.

Prefer controlled resolution/clarification semantics over arbitrary 0–1 confidence.

----------------------------------------------------------------------
4. AuthorisedKnowledgeScope
----------------------------------------------------------------------

Laravel owns AuthorisedKnowledgeScope.

It is derived only from authenticated user / workspace / stored permissions.

Access logic remains entirely outside the planner.

The prompt can never grant access.

The planner does not receive:
- user department;
- roles;
- access groups;
- raw permission rules.

Authorisation and prompt semantics remain independent.

The authorised scope defines the maximum search universe.

Nothing downstream may expand it.

----------------------------------------------------------------------
5. EligibilityResolver
----------------------------------------------------------------------

EligibilityResolver is explicitly Laravel-owned.

It is deterministic application/domain logic, not an AI component.

Input:

- RetrievalPlan
- AuthorisedKnowledgeScope
- authoritative ADR-0017 data

Output:

EligibleRetrievalScope

It resolves:

- CURRENT
- VALID_AT_DATE
- COMPARE
- approval/governance eligibility
- temporal authority
- version lineage
- ADR-0016 published + INDEXED prerequisites
- location applicability
- any other deterministic evidence-eligibility rule

It may only narrow AuthorisedKnowledgeScope.

Never expand it.

CLARIFICATION_REQUIRED short-circuits:
- EligibilityResolver is not invoked;
- Retriever is not invoked;
- no broad/current fallback search occurs.

ADR-0016’s dual visibility gate remains unchanged:

published Qdrant point
+
PostgreSQL INDEXED

ADR-0018 adds deterministic retrieval eligibility above that.

INDEXED must never be redefined to mean CURRENT or authoritative.

----------------------------------------------------------------------
6. Location / applicability semantics
----------------------------------------------------------------------

Consume ADR-0017’s OrganisationalLocation and per-version applicability model.

Keep access and applicability separate.

Authorisation answers:

“What may this user see?”

Applicability answers:

“Where does this version apply?”

A location reference in a prompt cannot grant access.

EligibleRetrievalScope must resolve applicability deterministically against the already-authorised scope.

UNIVERSAL applicability works across all locations permitted by the authorised scope.

Region applicability includes descendant Sites.

No free-text location filters.

----------------------------------------------------------------------
7. Metadata classification
----------------------------------------------------------------------

Preserve the three-way distinction:

Security metadata:
- workspace
- permissions
- access groups / grants
→ hard authorisation boundary

Eligibility metadata:
- approval
- temporal authority
- publication
- technical readiness
- version lineage
- location applicability
→ deterministic hard eligibility

Descriptive metadata:
- title
- subject
- tags
- document type
- owner
- organisational labels
- reference number
→ relevance / subject-resolution signals unless explicitly authoritative

Do not automatically turn semantic prompt terms into hard metadata filters.

Example:

“Show me the HR policy”

must not become:

department_id = HR

unless the authoritative metadata resolution independently proves that is the intended selector.

----------------------------------------------------------------------
8. EligibleRetrievalScope
----------------------------------------------------------------------

Define a provider-neutral, storage-neutral domain object.

It should express the exact evidence universe Python is allowed to search.

It should not expose:
- raw access rules;
- Laravel policy internals;
- arbitrary SQL;
- Qdrant DSL.

It should contain enough information to constrain retrieval safely and efficiently.

For ordinary modes, it represents one resolved evidence scope.

For COMPARE, it must preserve two independently-resolved sides.

----------------------------------------------------------------------
9. COMPARE semantics
----------------------------------------------------------------------

COMPARE is a genuine V1 requirement.

Examples:

- “What changed in the latest policy?”
- “Compare the current version with the 2022 version.”
- “How has this policy changed?”

The planner expresses symbolic anchors only.

EligibilityResolver resolves both sides independently.

The resolved scope must preserve:

PRIMARY / CURRENT side
and
COMPARISON / HISTORICAL side

or equivalent explicit labels.

Retriever searches each side independently.

Do NOT merge both sides into one candidate list.

RetrievalResult must preserve which side each evidence item belongs to.

If either side cannot be resolved safely:

COMPARISON_SCOPE_INCOMPLETE

No silent substitute version.

----------------------------------------------------------------------
10. Retriever contract
----------------------------------------------------------------------

Introduce a provider-neutral Retriever abstraction.

Input conceptually includes:

- original query;
- EligibleRetrievalScope;
- authoritative embedding-space generation;
- authoritative workspace-corpus generation;
- bounded candidate limit.

The Retriever:

- embeds the query using the compatible query embedding profile;
- validates embedding-profile compatibility;
- calls VectorStore;
- applies only the explicit resolved scope;
- hydrates authoritative chunk/provenance data;
- revalidates final evidence against authoritative PostgreSQL-backed eligibility where required by the architecture;
- returns candidate evidence.

The Retriever must NOT:

- authorise;
- determine CURRENT;
- resolve dates;
- interpret governance state;
- infer document lineage;
- answer;
- rerank.

Use candidate_k / candidate limit terminology rather than conflating broad retrieval size with final evidence count.

----------------------------------------------------------------------
11. RetrievalResult
----------------------------------------------------------------------

RetrievalResult must be a typed semantic result, not merely:

[]

or raw chunk text.

It should carry:

- controlled outcome classification;
- ranked candidates;
- raw retrieval score;
- rank;
- retrieval method;
- chunk identity;
- Document identity;
- DocumentFamily identity;
- version identity / lineage;
- provenance;
- embedding/retrieval lineage as appropriate.

Raw similarity scores must never be described as probabilities.

Do not duplicate authoritative metadata unnecessarily if it can be hydrated from PostgreSQL.

----------------------------------------------------------------------
12. Retrieval outcome taxonomy
----------------------------------------------------------------------

Define controlled semantic outcomes.

At minimum consider:

- EVIDENCE_FOUND
- NO_ELIGIBLE_EVIDENCE
- NO_SEMANTIC_MATCH
- TEMPORAL_SCOPE_UNRESOLVED
- COMPARISON_SCOPE_INCOMPLETE
- CLARIFICATION_REQUIRED
- RETRIEVAL_FAILED

These are internal semantic classifications.

User-facing wording is separate and must not leak sensitive existence/access information.

Security-sensitive failures must fail closed.

Never respond to an eligibility/authentication failure by widening retrieval.

----------------------------------------------------------------------
13. Laravel -> Python synchronous contract
----------------------------------------------------------------------

This is a genuine new decision ADR-0018 must settle.

All previous internal authentication ADRs were designed around:

Python worker
→ Laravel
for asynchronous ingestion.

Retrieval introduces:

Laravel
→ Python
synchronous, user-request critical path.

Do not silently reuse ADR-0009/0015/0016 worker HMAC semantics if the principal, direction, lease assumptions and failure behaviour do not fit.

Please compare reasonable options and recommend the V1 contract.

The contract should cover at least:

- authentication;
- request versioning;
- workspace context;
- request correlation / trace context;
- bounded request size;
- timeout behaviour;
- retry/idempotency posture;
- safe failures;
- privacy-safe telemetry.

No queue or worker lease is expected for synchronous retrieval.

----------------------------------------------------------------------
14. Observability / privacy
----------------------------------------------------------------------

Inherit ADR-0012.

Planner, eligibility orchestration and retrieval must not invent ad hoc logging.

Safe telemetry may include controlled fields such as:

- retrieval mode;
- outcome classification;
- candidate count;
- eligible-scope size;
- durations;
- embedding profile classification;
- generation IDs;
- retrieval method;
- failure classification.

Do not capture by default:

- raw user question;
- document/chunk text;
- vectors;
- credentials;
- signatures;
- provider payloads.
