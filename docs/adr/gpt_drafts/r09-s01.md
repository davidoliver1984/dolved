## Architectural context
Phase 8 established:
- PostgreSQL as the authoritative system of record for Document identity,
  workspace ownership and lifecycle;
- the lifecycle transition `UPLOADING → UPLOADED`;
- Laravel as owner of the Document lifecycle;
- direct browser-to-S3 uploads through LocalStack locally and AWS S3 in
  production;
- server-side object verification before a Document becomes `UPLOADED`.
Phase 9 introduces asynchronous ingestion:
```text
UPLOADED
↓
QUEUED
↓
PROCESSING

Laravel must both:

1. transition an eligible Document from UPLOADED to QUEUED; and
2. publish a versioned document-ingestion request to SQS.

PostgreSQL and SQS cannot participate in one native atomic transaction.

A naïve direct publication design creates a dual-write failure:

Database commits but SQS publication fails
→ Document is QUEUED but no message exists

The reverse operation order is also unsafe:

SQS publication succeeds but the database transaction fails
→ a worker receives an event for uncommitted lifecycle state

Proposed decision

Adopt the Transactional Outbox Pattern for ingestion-event publication.

Within one PostgreSQL transaction, Laravel will:

1. verify that the Document is eligible for ingestion;
2. transition the Document from UPLOADED to QUEUED;
3. persist an outbox record containing the versioned ingestion event and its
    stable event identifier.

A separate publisher process will:

1. locate unpublished outbox records;
2. validate the payload against the canonical event contract;
3. publish the event to LocalStack SQS locally or AWS SQS in production;
4. mark the outbox record as published only after successful publication;
5. retry transient publication failures.

The outbox provides durable publication intent, not exactly-once delivery.

SQS remains an at-least-once delivery mechanism. A publisher may successfully
send an event and fail before recording publication success. Duplicate
publication and duplicate delivery must therefore be tolerated.

Consumers must be idempotent using the logical event identifier rather than
relying solely on the SQS transport message identifier.

Required ADR coverage

The ADR should clearly explain:

Context

* why Phase 9 creates a PostgreSQL/SQS dual-write problem;
* why an ordinary Laravel database transaction cannot atomically include SQS;
* failure scenarios when publishing before or after the database transaction;
* why queue publication from a model observer, listener or HTTP controller
    does not solve atomicity.

Decision

* use a PostgreSQL-backed transactional outbox;
* write the Document lifecycle transition and outbox record in one transaction;
* publish asynchronously after commit;
* retain unpublished records when SQS is unavailable;
* mark records as published only after confirmed SQS publication;
* use a stable logical event identifier across publication retries;
* preserve workspace and correlation context;
* validate outbox payloads against the shared versioned event contract;
* treat delivery as at least once;
* require idempotent consumers;
* keep Laravel authoritative for lifecycle state.

Clarify that “transactional” refers to the transaction between the Document
change and outbox persistence inside PostgreSQL. It does not make PostgreSQL
and SQS one distributed transaction.

Ownership and boundaries

* PostgreSQL owns the durable publication intent;
* SQS transports ingestion requests;
* Laravel owns Document lifecycle state;
* Python consumes events but does not directly update Laravel-owned tables;
* event publication infrastructure must remain outside the Document model;
* controllers should not publish directly to SQS.

Expected outbox semantics

Describe conceptually, without prematurely fixing every column name:

* stable event identifier;
* event type;
* event version;
* aggregate or Document identifier;
* workspace identifier;
* correlation identifier;
* payload;
* occurrence timestamp;
* publication timestamp;
* publication attempt information where useful.

Discuss safe concurrent publisher behaviour, such as row claiming or locking,
without forcing a specific implementation unless existing project conventions
already settle it.

Discuss retention and cleanup at an architectural level. Published rows should
not grow forever, but deletion or archival policy may remain configurable and
be implemented later.

Failure and retry behaviour

Cover:

* PostgreSQL transaction failure;
* SQS being unavailable;
* successful publish followed by publisher failure before marking the row;
* duplicate publication;
* duplicate SQS delivery;
* poison or permanently invalid outbox payloads;
* preserving diagnostic information;
* avoiding infinite tight retry loops.

Distinguish publisher retry behaviour from SQS consumer retry and dead-letter
behaviour.

Alternatives considered

At minimum assess:

1. Publish directly to SQS after the database commit.
2. Publish to SQS before the database commit.
3. Dispatch from an Eloquent model observer or Laravel event listener.
4. Use only Laravel’s database queue.
5. Use a distributed transaction or two-phase commit.
6. Use change-data capture instead of an application-managed outbox.
7. Periodically scan all QUEUED Documents and reconstruct missing events.

For each alternative, state why it was not selected for this platform now.

The Laravel database queue alternative should be discussed fairly: it could
avoid the PostgreSQL/SQS dual write if it became the actual transport, but it
would conflict with the accepted AWS SQS architecture and Python consumer
boundary.

Change-data capture should be recognised as a valid larger-scale alternative,
but excessive operational complexity for the current platform stage.

Consequences

Include both benefits and costs.

Benefits should include:

* no silent loss of publication intent after a committed lifecycle transition;
* atomic consistency between QUEUED state and durable event intent;
* resilience during temporary SQS outages;
* auditable event publication state;
* controlled retries;
* clear producer responsibilities.

Costs should include:

* an additional table and persistence model;
* a separate publisher process;
* duplicate publication remains possible;
* idempotent consumers remain mandatory;
* retention and operational monitoring are required;
* eventual rather than immediate queue publication;
* more tests and failure modes to maintain.

Scope boundaries

State explicitly that this ADR does not define:

* the exact JSON event schema, which belongs to R09-S01 contract work;
* every outbox database column;
* the final polling interval or batch size;
* consumer processing logic;
* text extraction;
* chunking;
* embeddings;
* vector indexing;
* document failure semantics during actual ingestion;
* a generic enterprise event bus for every future domain event.

The initial decision applies to document-ingestion request publication. Any
broader platform-wide adoption should be deliberate rather than assumed.

Operational implications

Mention:

* publisher health and backlog observability;
* unpublished-event count and oldest-event age;
* publication attempt and failure logging;
* correlation identifiers;
* graceful publisher shutdown;
* LocalStack SQS locally and AWS SQS in production;
* testing database rollback, SQS outage and duplicate-publication scenarios.
