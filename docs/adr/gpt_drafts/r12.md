# ADR purpose

ADR-0013 should define the provider-neutral embedding architecture and embedding contract for dolved.

Phase 13 takes immutable chunks produced by Phase 11 and converts their semantic content into vectors that the later vector-storage and retrieval phases can use.

The ADR must distinguish clearly between:

- the architectural embedding boundary;
- the initial V1 provider choice;
- later vector persistence and collection topology;
- retrieval, reranking, generation and evaluation concerns that do not belong to Phase 13.

# Decisions to record in ADR-0013

## Provider boundary

Define an application-owned, provider-neutral `Embedder` abstraction.

The pipeline must depend on the abstraction rather than directly on the Voyage SDK or API.

The contract should support additive future implementations such as:

- another hosted embedding provider;
- Amazon Bedrock/Titan;
- a locally hosted embedding model;
- a deterministic fake used by tests.

The architecture must not imply that switching provider is operationally free. Changing provider, model, dimensions or any incompatible embedding configuration requires controlled re-embedding.

## Initial V1 provider

Record Voyage as the initial hosted V1 embedding provider.

The reason is retrieval quality and low operational responsibility, not AWS alignment or provider lock-in.

Local model hosting is deliberately deferred because V1 does not need the infrastructure, maintenance, capacity-planning or model-lifecycle responsibility.

The provider remains replaceable through the `Embedder` contract.

## Embedding timing and workflow

Embedding occurs asynchronously as part of ingestion after:

1. extraction;
2. structural normalisation;
3. chunking.

The browser upload itself does not call the embedding provider.

The provider receives only the chunk text and the minimum semantic configuration required for embedding.

It must not receive:

- the original uploaded file;
- workspace credentials;
- storage credentials;
- unrelated user details;
- provenance metadata it does not need.

During search, the user question is embedded using the active compatible embedding profile before vector retrieval.

Stored document vectors are reused; documents are not re-embedded for every question.

## Explicit embedding purposes

The request contract must distinguish at minimum between:

- document/chunk embedding;
- query embedding.

Where a provider supports task-specific input modes, those modes must be explicit and retained as consequential configuration.

## Embedding profile and lineage

Define an immutable typed embedding profile containing the consequential facts that determine vector compatibility and behaviour, including where applicable:

- provider identity;
- model identity;
- model revision/version where the provider exposes one;
- output dimensions;
- vector data type;
- normalisation behaviour;
- document/query task modes;
- adapter version;
- other consequential model parameters.

The profile must have:

- a canonical inspectable snapshot;
- a deterministic fingerprint derived from that snapshot.

The fingerprint represents vector compatibility and must be retained with produced embedding results.

A bare mutable model name is not sufficient lineage where model behaviour may change underneath it.

The ADR must be honest about hosted-provider reproducibility: exact attribution and compatibility protection are required, but permanent bit-for-bit reproducibility must not be promised where a provider does not expose an immutable model revision.

## Compatibility invariant

Vectors created by incompatible embedding profiles must never be treated as belonging to the same searchable vector generation.

Matching dimensions alone do not make two embedding spaces compatible.

A query may search a vector generation only using its compatible embedding profile.

The exact Qdrant collection/generation topology belongs to the vector-storage phase, but ADR-0013 must establish this invariant now.

## Controlled re-embedding

A consequential embedding-profile change must create a new vector generation and trigger controlled re-embedding of the relevant active chunks.

Do not update an active corpus piecemeal in place while mixing old and new vector spaces.

The eventual workflow should support:

1. existing generation remains active;
2. create new generation for the new profile;
3. re-embed all required chunks;
4. verify completeness and dimensions;
5. atomically activate the new generation;
6. retire the previous generation later.

The persistence and activation mechanics remain deferred to the vector-storage phase.

## Batch contract

The embedding boundary should accept bounded batches rather than requiring one provider request per chunk.

Each requested item must retain its source chunk identity.

The result must preserve a one-to-one association between requested chunk identities and returned vectors.

The implementation must validate:

- response count;
- dimensions;
- finite numeric values;
- item association/order;
- profile compatibility.

Batch limits must be configurable and constrained by provider limits such as:

- maximum input count;
- aggregate token/input size;
- payload size.

## Semantic result versus operational telemetry

The semantic embedding result should contain the facts required to understand and persist the vectors, including:

- embedding profile snapshot and fingerprint;
- source chunk identity;
- produced vector;
- dimensions;
- any consequential provider-returned semantic metadata.

Operational telemetry remains separate and may include safe allowlisted facts such as:

- provider;
- model classification;
- item count;
- token usage;
- request duration;
- provider call count;
- retry count;
- estimated cost;
- controlled failure classification.

Raw chunk text, query text and vectors must not be exported to telemetry by default.

This must remain consistent with ADR-0012.

## Typed failures and retries

Translate provider-specific exceptions into typed platform failures.

Differentiate at minimum between categories such as:

- invalid or empty input;
- input too large;
- authentication/configuration failure;
- rate limiting;
- timeout;
- temporary provider unavailability;
- malformed provider response;
- dimension mismatch;
- profile mismatch.

Retry only genuinely transient failures.

Use bounded retries with capped exponential backoff and jitter.

Permanent validation, credential, dimension and compatibility failures must not be retried as though they were transient.

Failures and retries must be visible in safe telemetry and auditing where operationally significant.

## Testing

Ordinary automated tests must not require:

- live internet access;
- Voyage credentials;
- paid provider calls.

Provide a deterministic fake embedder that:

- produces the same fixed-dimension vector for the same input and profile;
- preserves item identity;
- supports batch behaviour;
- can simulate each typed failure;
- supports completeness and validation tests.

Real Voyage integration tests should be isolated, opt-in and clearly distinguishable from the normal test suite.

The fake tests contract correctness, not semantic retrieval quality.

## Secrets

Provider credentials must remain outside domain models, logs, telemetry and persisted semantic results.

They belong to environment/secret-management configuration.

## Scope boundaries

ADR-0013 must explicitly defer:

- Qdrant collection and vector-generation topology;
- vector persistence;
- dense retrieval settings;
- sparse/keyword retrieval;
- hybrid fusion;
- reranking;
- retrieval thresholds and abstention;
- query decomposition;
- prompt construction;
- generation;
- citation design;
- evaluation implementation.

# Additional V1 decisions to preserve outside ADR-0013

We have also agreed the following V1 direction. These decisions do not all belong inside the embedding ADR, but they must not be lost.

Please inspect the current roadmap and implementation sequence, then propose precise documentation/task updates that place each at the earliest technically valid future stage without moving or renumbering completed phases unnecessarily.

## Retrieval quality direction

V1 should include:

- dense semantic retrieval;
- sparse/keyword retrieval where practical;
- hybrid candidate fusion, with RRF as the initial likely method;
- provider-neutral reranking;
- Voyage as the initial reranking provider;
- retrieval of a broader candidate set before reranking;
- reranking down to a smaller evidence set;
- calibrated evidence thresholds;
- explicit abstention where the system cannot find sufficient evidence;
- hard workspace, authorisation, active-document and lifecycle filters;
- basic handling for obsolete/archived documents;
- preservation of source identity and provenance through retrieval and reranking.

## Query decomposition

The retrieval architecture must be designed so query decomposition can be enabled later without rewriting the retrieval pipeline.

The intended shape is:

User query
    -> query-planning boundary
    -> one or more bounded retrieval queries
    -> retrieve each query
    -> merge and deduplicate evidence
    -> rerank against the original user question
    -> generate one grounded answer

For initial V1 operation, decomposition should be disabled by default or use an identity/no-op planner that returns only the original query.

A future model-assisted planner may return a small bounded set of subqueries for compound questions.

The design must support this additive implementation, but automatic decomposition must not be enabled until repository-owned evaluation demonstrates sufficient quality benefit to justify its extra model call, latency, cost and complexity.

Record this as a roadmap/design constraint now and formalise it in the future retrieval ADR.

## Evaluation foundation

V1 must include a repository-owned evaluation harness that grows with the pipeline.

It should eventually support:

- representative source documents;
- labelled questions;
- expected relevant documents/elements/chunks;
- reference answers or required answer facts where appropriate;
- answerable and unanswerable questions;
- exact-wording and paraphrased questions;
- table-based questions;
- multi-evidence questions;
- conflicting-document cases;
- obsolete/current-document cases;
- cross-workspace and authorisation cases;
- adversarial and prompt-injection cases.

Metrics should include where applicable:

- Recall@k;
- MRR;
- nDCG;
- context precision;
- context recall;
- faithfulness;
- answer correctness/relevancy;
- citation support;
- abstention accuracy;
- latency;
- token usage;
- provider cost.

Ragas may be used for suitable LLM/RAG evaluation metrics, but the labelled corpus, deterministic retrieval metrics and experiment records must remain repository-owned and framework-independent.

## Quality lineage

Every answer or evaluation result should eventually be attributable to the quality-affecting configuration used, including:

- extraction/parser identity where relevant;
- normaliser version;
- chunking strategy/profile;
- embedding profile;
- vector generation;
- retrieval configuration;
- sparse retrieval configuration;
- fusion method/configuration;
- reranker provider/model/profile;
- query-planner identity/configuration where used;
- prompt-template version;
- generation provider/model/configuration.

Do not force all of these into ADR-0013. Record the cross-cutting constraint now and ensure each future ADR owns the specific lineage it introduces.

## Quality release gates

Before a consequential quality-affecting configuration or provider change reaches production, the project should run the accepted evaluation corpus and compare it against the current baseline.

At minimum, the future gate should protect:

- retrieval recall;
- reranking quality;
- faithfulness;
- citation support;
- correct abstention;
- workspace isolation and authorisation;
- unacceptable latency or cost regression.

The gate may begin as a documented/manual acceptance step and later become automated in CI.
