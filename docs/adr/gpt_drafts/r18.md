----------------------------------------------------------------------
Architectural direction
----------------------------------------------------------------------

I agree with Codex’s recommended Option A:

Repository-owned evaluation harness with optional framework adapters.

The platform owns:

- a versioned evaluation corpus;
- the corpus schema;
- stable case/source identities;
- relevance judgements;
- deterministic metrics;
- experiment records;
- accepted baselines;
- quality-gate policies;
- release decisions;
- machine-readable and human-readable reports.

External frameworks such as Ragas may be used through adapters for suitable model-assisted metrics.

External evaluation frameworks do NOT own:

- the corpus;
- the corpus schema;
- result formats;
- baseline lineage;
- quality-gate policy;
- release approval.

The evaluation architecture must remain framework-neutral in the same spirit as Embedder, VectorStore, RetrievalPlanner, Retriever and Reranker.

----------------------------------------------------------------------

1. Core principle
----------------------------------------------------------------------

The governing principle should be:

“Every retrieval architecture change must be measurable against a repository-owned evaluation corpus before it can be considered an improvement.”

Evaluation must distinguish:

- deterministic correctness;
- retrieval quality;
- operational performance;
- later model-assisted quality.

Do not collapse everything into one composite “RAG score.”

The harness must make it possible to identify where a regression began.

----------------------------------------------------------------------

2. Evaluation corpus ownership
----------------------------------------------------------------------

The corpus belongs to the repository.

It must be safe to:

- commit;
- run locally;
- run in CI;
- use in development;
- use with supported external evaluators/providers.

Corpus source material must therefore be:

- synthetic;
- appropriately licensed;
- or deliberately sanitised.

Do not use customer documents as the repository’s canonical evaluation dataset.

The corpus must be explicitly versioned.

Once a corpus version has been used for an accepted baseline, it must be immutable.

Correcting/changing labels, expectations or source material creates a new corpus version rather than silently changing historical benchmark meaning.

----------------------------------------------------------------------

3. Stable semantic case identity
----------------------------------------------------------------------

Evaluation case identity must be independent of exact question wording.

A stable semantic case may have multiple phrasing variants.

Conceptually:

case_id:
    temporal-policy-017

variants:
    - “What was the sickness policy in 2022?”
    - “How did sickness absence work during 2022?”
    - another semantically-equivalent paraphrase

The case represents one underlying information need.

Question wording variants test robustness to natural-language phrasing.

Do not treat every paraphrase as an unrelated business case when it represents the same semantic intent.

Case IDs must remain stable across corpus versions where the underlying semantic case is genuinely the same.

----------------------------------------------------------------------

4. Separate expectation layers
----------------------------------------------------------------------

Do not create one undifferentiated “expected” object.

The corpus should record expectations separately for the stages ADR-0018 defined.

At minimum distinguish:

Planner expectations:
- expected temporal mode;
- expected comparison anchors;
- expected applicability reference;
- clarification expectation where relevant.

Eligibility expectations:
- expected eligible DocumentFamily / Document versions;
- expected temporal authority;
- expected applicability resolution;
- expected controlled eligibility outcome;
- expected absence of unauthorised/ineligible versions.

Retrieval relevance expectations:
- expected relevant source evidence;
- graded relevance where appropriate;
- required evidence sets for multi-evidence questions.

Outcome expectations:
- expected semantic RetrievalResult classification where applicable.

Later extension points may add:

- reference facts;
- expected answer properties;
- citation expectations;
- faithfulness expectations;
- abstention expectations;
- adversarial expectations.

This separation should allow a failed run to answer:

Did planning fail?
Did eligibility fail?
Did retrieval fail?
Did ranking fail?

rather than merely “the case failed.”

----------------------------------------------------------------------

5. Stable evidence/relevance identifiers
----------------------------------------------------------------------

Ground truth must not depend solely on generated chunk IDs.

Chunk IDs may legitimately change when:

- chunking strategy changes;
- chunk size/overlap changes;
- extraction/normalisation changes.

The evaluation architecture exists partly to compare those changes.

Therefore relevance labels should be anchored against stable source concepts such as:

- source document/version identity;
- source element identity where sufficiently stable;
- page/section/structural source location;
- canonical source spans or other deliberately stable evidence references.

Please critique exactly which identity level is safest given ADR-0010/0011’s identity rules.

The goal is:

different chunking strategies can still be compared against the same underlying ground truth.

A metric adapter may map retrieved chunks back onto stable source evidence before computing relevance.

----------------------------------------------------------------------

6. Required V1 case families
----------------------------------------------------------------------

The repository corpus should deliberately cover the architecture we have actually built.

At minimum include cases for:

Natural-language robustness:
- exact wording;
- paraphrases;
- synonymous terminology.

Document structure:
- prose;
- tables;
- multi-evidence questions;
- evidence spanning multiple chunks/elements.

Temporal authority:
- CURRENT;
- VALID_AT_DATE;
- COMPARE;
- scheduled future versions;
- late approval;
- withdrawn versions;
- versions that never attained authority;
- authority gaps;
- no predecessor resurrection.

Applicability:
- UNIVERSAL;
- site-specific;
- region-specific;
- descendant-site applicability;
- location aliases;
- ambiguous applicability references.

Security/isolation:
- cross-workspace exclusion;
- unauthorised evidence;
- access-limited cases.

Retrieval outcomes:
- empty eligible scope;
- zero retrieval candidates;
- clarification required;
- comparison-side incomplete;
- temporal scope unresolved where valid.

Adversarial:
- prompt injection inside document content;
- misleading or conflicting evidence;
- documents attempting to instruct the model/system;
- malformed/adversarial metadata where useful.

Please distinguish what can be meaningfully evaluated in Phase 16 retrieval from what belongs later to answer-generation evaluation.

Do not force generation-only cases into retrieval metrics prematurely.

----------------------------------------------------------------------

7. Layered evaluation
----------------------------------------------------------------------

The harness should evaluate separate layers.

Layer 1 — RetrievalPlanner correctness

Evaluate:
- temporal mode;
- symbolic anchors;
- applicability reference;
- clarification behaviour.

Planner accuracy must be evaluated separately from downstream retrieval.

Layer 2 — Eligibility correctness

Evaluate:
- AuthorisedKnowledgeScope narrowing;
- CURRENT / VALID_AT_DATE / COMPARE resolution;
- governance eligibility;
- temporal authority;
- applicability;
- tenant isolation;
- controlled outcomes.

Layer 3 — Retrieval relevance/ranking

Evaluate:
- relevant evidence retrieved;
- ordering;
- coverage;
- noise.

Layer 4 — Operational behaviour

Evaluate:
- latency;
- token usage;
- provider cost;
- request counts where useful.

Later, generation evaluation may add:
- answer correctness;
- faithfulness;
- citation support;
- abstention;
- answer completeness.

Those later metrics are extension points, not Phase 16 implementation requirements unless explicitly needed by this ADR’s architecture.

----------------------------------------------------------------------

8. Deterministic retrieval metrics
----------------------------------------------------------------------

At minimum support:

- Recall@K;
- Precision@K;
- MRR;
- nDCG.

Please define what relevance grading means for nDCG in this corpus without over-specifying implementation details.

Metrics must be reproducible from the same deterministic inputs.

Do not treat vector similarity scores as metric ground truth.

Do not invent release thresholds in this ADR.

R16-S06 should produce the first measured baseline before numerical regression tolerances are selected.

----------------------------------------------------------------------

9. Important slices are first-class
----------------------------------------------------------------------

Aggregate metrics must never be allowed to hide important failures.

The experiment result should expose first-class slice metrics for important case families, including at minimum:

- CURRENT;
- VALID_AT_DATE;
- COMPARE;
- tables;
- multi-evidence;
- applicability/location;
- paraphrase;
- cross-workspace;
- unauthorised;
- zero-evidence;
- adversarial.

Please decide whether slice definitions belong to:

- corpus metadata;
- quality-gate policy;
- or both.

The architecture must make it possible to add new slices later without changing the core evaluation result format.

----------------------------------------------------------------------

10. Absolute invariants versus comparative quality
----------------------------------------------------------------------

Some failures are absolute release blockers.

At minimum:

- cross-workspace evidence returned;
- unauthorised evidence returned;
- temporally ineligible evidence returned;
- organisationally/applicability-ineligible evidence returned;
- silently skipped/lost evaluation cases;
- deterministic metric non-reproducibility.

These must fail regardless of aggregate Recall/MRR/nDCG improvements.

Other metrics are comparative against an explicitly accepted baseline:

- Recall@K;
- Precision@K;
- MRR;
- nDCG;
- planner quality;
- latency;
- cost.

Do not allow a quality improvement in one area to compensate for a tenancy/security correctness failure.

----------------------------------------------------------------------

11. Accepted baselines
----------------------------------------------------------------------

Experiment run and accepted baseline are separate concepts.

A candidate run never automatically becomes the baseline.

Baseline promotion must be deliberate and independently recorded.

The system must prevent the anti-pattern:

change system
→ benchmark regresses
→ overwrite baseline
→ benchmark “passes”

An accepted baseline should record enough lineage to explain exactly what system configuration produced it.

Updating a baseline is a governance/release action, not merely writing the latest metrics to a file.

----------------------------------------------------------------------

12. Experiment lineage
----------------------------------------------------------------------

Every evaluation experiment should record enough information to interpret or reproduce the result.

At minimum consider:

- repository commit;
- corpus version;
- quality-gate-policy version;
- evaluation-harness version;
- planner provider/model/configuration;
- embedding-profile fingerprint;
- chunking strategy/configuration;
- retrieval configuration;
- candidate_k;
- evaluator identity/configuration;
- execution timestamp;
- latency;
- token usage;
- estimated provider cost.

Later additions may include:
- reranker provider/model;
- sparse/hybrid configuration;
- generation model;
- prompt/configuration lineage.

Please avoid coupling the schema to currently-selected providers.

----------------------------------------------------------------------

13. Quality-gate policy
----------------------------------------------------------------------

Quality-gate policy itself should be versioned.

Do not hard-code release thresholds invisibly inside test code.

The policy should define:

- absolute hard failures;
- comparative metric requirements;
- important slices;
- allowed regression tolerances once calibrated;
- which metrics are advisory versus blocking.

Initial numerical tolerances should NOT be invented now.

R16-S06 should record the first baseline and provide the empirical information required to choose meaningful tolerances.

----------------------------------------------------------------------

14. Initial manual release gate
----------------------------------------------------------------------

V1 should initially use a documented human-reviewed release gate rather than automatically promoting any configuration that numerically wins.

An evaluation run produces:

- a machine-readable result;
- a readable comparison report.

A reviewer then records:

- accepted;
- rejected;
- or a reasoned, time-bounded waiver.

A waiver must not silently rewrite the accepted baseline.

Baseline promotion remains a separate deliberate action.

Keep this lightweight — do not build a broad approval/workflow engine.

----------------------------------------------------------------------

15. Model-assisted evaluators and Ragas
----------------------------------------------------------------------

Ragas may be supported as an evaluator adapter.

It does not own the evaluation architecture.

Likewise future evaluators/frameworks must be replaceable.

Introduce an evaluator boundary if warranted, e.g. provider/framework-neutral model-assisted evaluator abstraction.

Model-assisted metrics should initially be advisory unless stability/reproducibility has been demonstrated.

A model judge must never be the sole authority for deterministically testable properties such as:

- workspace isolation;
- authorisation;
- temporal eligibility;
- applicability;
- deterministic relevance identities;
- later citation existence/support where direct deterministic checking is possible.

Please compare the value of introducing an explicit evaluator adapter contract now versus leaving adapters as harness plugins until the first model-assisted evaluator is actually implemented.

Do not over-abstract without a real V1 use.

----------------------------------------------------------------------

16. Reports
----------------------------------------------------------------------

The harness should produce both:

Machine-readable experiment result:
- suitable for automated comparison;
- stable/versioned schema;
- usable by later CI tooling.

Human-readable report:
- baseline vs candidate;
- overall metrics;
- slice metrics;
- hard failures;
- regressions/improvements;
- latency/cost differences;
- experiment lineage;
- waiver/baseline status where relevant.

Do not make a third-party dashboard the authoritative record.

----------------------------------------------------------------------

17. Golden regressions
----------------------------------------------------------------------

When a real retrieval defect is discovered and fixed, it should be possible to preserve that failure as a permanent regression case.

Golden regression cases are part of the repository-owned corpus, not ad hoc tests outside it.

They must retain:

- stable case identity;
- explanation of the original failure;
- expected planner/eligibility/retrieval behaviour as appropriate.

The evaluation corpus should become more valuable over time as real failures are added.

----------------------------------------------------------------------

18. Privacy and observability
----------------------------------------------------------------------

Inherit ADR-0012.

Evaluation telemetry/reporting must not accidentally capture sensitive external/customer data.

The repository corpus is deliberately safe/sanitised, but the harness architecture should still preserve the same privacy boundaries.

Record identifiers, classifications, metrics and lineage.

Do not capture arbitrary provider request/response bodies merely because evaluation is “non-production.”

----------------------------------------------------------------------

19. Out of scope
----------------------------------------------------------------------

Do NOT decide here:

- hybrid retrieval architecture — R16-S07;
- reranker provider or detailed contract — R16-S07;
- calibrated evidence thresholds — later retrieval/evaluation work after baseline evidence exists;
- generation evaluation details beyond forward-compatible schema seams;
- answer generation;
- citation generation;
- customer-specific production evaluation datasets;
- broad automated release orchestration;
- external evaluation dashboard products.

----------------------------------------------------------------------

20. Alternatives considered
----------------------------------------------------------------------

Explicitly compare:

Option A — repository-owned harness with optional framework adapters
Recommended.

Option B — Ragas-first architecture
Faster initially, but makes a third-party framework’s corpus/result abstractions architectural dependencies.

Option C — entirely bespoke evaluation with no external evaluator integration
Maximum control but recreates useful model-assisted evaluation capability unnecessarily.

Please challenge Option A if you identify a better design, but do not choose a framework-first architecture merely for convenience.
