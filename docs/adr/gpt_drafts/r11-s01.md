Please draft the first version of ADR-0011 for Phase 11 (R11-S01).

This ADR should be written in the same style and quality as the previous accepted ADRs. It should describe the architecture and the reasoning behind the decisions, not just list implementation details.

Before drafting, please take into account everything we have already established for Phase 11.

## Overall architectural goal

Chunking is a deterministic, versioned transformation from one immutable NormalisedDocument into one immutable ChunkingResult.

The purpose of this ADR is to define the architectural contract for chunking, not the specific chunking algorithm.

The exact chunk sizing heuristics, overlap percentages, semantic chunking and future AI-assisted strategies are intentionally out of scope for this ADR.

---

## Confirmed architectural decisions

Please treat the following as settled decisions rather than open questions.

### 1. Chunking boundary

ChunkingStrategy accepts:

    ChunkingStrategy.chunk(document: NormalisedDocument)

and returns:

    ChunkingResult

Do not introduce a ChunkingContext or ChunkingInput wrapper.

Reason:

NormalisedDocument already carries its own business identity (workspace_id, document_id). A context object is only appropriate where the input artefact cannot intrinsically carry identity.

ExtractionContext exists because raw byte streams have no identity.

NormalisedDocument is already a self-describing domain model.

The ADR should explain this architectural principle.

---

### 2. Deterministic transformation

Chunking is a deterministic transformation.

Repeated execution with:

- identical NormalisedDocument
- identical strategy
- identical strategy version
- identical consequential configuration

must produce the same semantic chunk set.

---

### 3. Immutable contracts

NormalisedDocument is immutable.

ChunkingResult is immutable.

Chunk is immutable.

The chunker must never mutate its input.

---

### 4. Pluggable strategy boundary

The pipeline depends on the ChunkingStrategy abstraction, not a concrete implementation.

The initial implementation is a deterministic structural baseline strategy.

Future strategies may include semantic, contextual or model-assisted chunking without changing downstream consumers.

---

### 5. Chunk provenance

Chunks are retrieval units, not simple substrings.

Each chunk preserves provenance.

A chunk may span multiple source elements.

Each source contribution remains attributable back to the originating normalised element.

This provenance exists to support future citation, inspection and traceability.

This ADR should preserve the required provenance without designing the future citation system.

---

### 6. Identity

Chunk identities should be deterministic derived identities.

The ADR should describe that chunk identity is derived from the semantic inputs that define the chunk (document identity, strategy identity/version, configuration fingerprint, ordinal/provenance, etc.), rather than random UUID generation.

The exact implementation can remain implementation detail.

---

### 7. No persistent extraction identity

Please reflect an important architectural principle that has already been established:

Extraction is treated as a transient transformation rather than a durable domain entity.

Accordingly, there is no persistent extraction identifier.

Chunking continues from the immutable NormalisedDocument rather than referencing an extraction run.

Avoid wording such as "object existing in memory"; instead explain this in architectural terms.

---

### 8. Token counting

Token counts should be reproducible.

Tokenizer identity belongs to the chunking configuration rather than being duplicated on every individual chunk.

Each chunk records its token count.

The configuration records which tokenizer produced those counts.

---

### 9. ChunkingResult

ChunkingResult represents the result of one deterministic chunking operation.

It should conceptually contain:

- strategy identity
- strategy version
- configuration snapshot/fingerprint
- produced chunks
- warnings
- usage information where appropriate

Execution telemetry (timings etc.) should be kept conceptually separate from the semantic result.

---

### 10. Invariants

The ADR should define architectural invariants including:

- no mutation of input
- deterministic output
- no silent text loss
- source provenance preserved
- chunk ordering preserved
- strategy/version/configuration retained
- future extensibility through ChunkingStrategy

---

## Deferred decisions

Please explicitly defer:

- baseline chunk sizes
- overlap algorithm
- semantic chunking
- AI-assisted chunking
- contextual summarisation
- embedding implementation
- vector database persistence
- retrieval
- citation lifecycle
- re-extraction lifecycle

Those belong to later phases.

---

The ADR should read as though it naturally follows ADR-0010 and should establish a durable architectural contract that later chunking implementations can conform to.
