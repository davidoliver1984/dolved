Agreed decisions

1. A Workspace is the platform’s tenant, collaboration and data-isolation boundary.
2. Do not introduce a separate organisation hierarchy at this stage.
3. Users are global identities and may belong to multiple workspaces.
4. The user-to-workspace relationship is represented by a first-class WorkspaceMembership domain model rather than an anonymous pivot.
5. Initial membership roles are fixed: owner, admin and member.
6. Custom roles and a granular permission engine are deferred.
7. Each workspace has exactly one active owner membership.
8. created_by_user_id records creation provenance but is not the source of current ownership authority.
9. Memberships represent users who have joined a workspace. Invitations will be modelled separately in a later session.
10. Tenant context is explicit in workspace-scoped API routes using immutable public identifiers.
11. A remembered current workspace may be used by the frontend as a navigation preference, but it is not an authorisation or isolation mechanism.
12. The relational tenancy model is pooled: one shared PostgreSQL database and shared tables.
13. Every workspace-owned relational row must contain a non-nullable workspace foreign key.
14. Laravel isolation will be enforced through workspace-scoped routes, active-membership validation, workspace-scoped resource resolution, policies and negative cross-tenant tests.
15. Hidden global Eloquent scopes are not the primary security boundary.
16. PostgreSQL Row-Level Security is not implemented in Phase 7. It remains a deliberate future defence-in-depth option requiring its own design, connection-context handling and tests.
17. Workspace identity must propagate through all derived artefacts and service boundaries, including object-storage keys, queue events, extracted documents, chunks, vectors and retrieval filters.
18. Asynchronous workers must not infer workspace context from browser sessions or process-global mutable state.
19. Consumers must validate that an event’s referenced resource belongs to the workspace identified by the event.
20. Shared S3-compatible storage will use server-controlled workspace-prefixed object keys. A path prefix is not itself an authorisation mechanism.
21. Every vector or retrieval record must retain immutable workspace identity. The final Qdrant collection and sharding strategy remains deferred to R13-S01.
22. Registration creates a global user identity only.
23. Workspace creation is explicit and atomically creates the workspace and its owner membership.
24. Workspace deletion is deferred and will later be designed as a distributed lifecycle across PostgreSQL, object storage and vector storage.
25. Every persistent entity must be classified as platform-global, workspace-relationship or workspace-owned.

Required security invariants

The ADR must clearly state that:

* authentication does not grant workspace access;
* workspace access requires active membership;
* roles are scoped to a single workspace;
* client-supplied workspace identity is never trusted without membership validation;
* tenant-owned resources are resolved inside the workspace boundary before action authorisation;
* cross-workspace access fails closed;
* a workspace may never be left without an active owner;
* tenant identity is preserved through all synchronous and asynchronous processing stages;
* storage prefixes and vector payloads support scoping but do not replace authorisation;
* negative cross-tenant tests are mandatory for tenant-owned features;
* the repository must not claim PostgreSQL RLS until it is genuinely implemented and verified.

* automatic personal workspace creation during registration;

Do not portray rejected options as universally wrong. Explain why they are not the best current fit for this platform.

Consequences to capture

Positive consequences:

* explicit and testable tenant context;
* users may collaborate across several workspaces;
* conventional pooled SaaS operations;
* clear propagation into Laravel, Python, SQS, S3 and Qdrant;
* future compatibility with RLS, enterprise hierarchy and tiered vector isolation.

Costs and risks:

* every tenant-owned query requires disciplined scoping;
* pooled tenancy increases the impact of an isolation defect;
* role and owner invariants require careful transactional enforcement;
* distributed deletion and export will require orchestration;
* negative isolation tests are mandatory;
* future RLS adoption requires deliberate connection-context design.
