  We are working on:

  Phase 8 — Document Domain and Storage
  Stage 8.1 — Define Document Lifecycle

  Purpose

  Define the lifecycle of a document before any persistence or upload implementation begins.

  The document model should become the durable architectural contract that later stages (uploads, ingestion, chunking, embeddings, retrieval and administration) build upon.

  The ADR should discuss and justify:

  - What a Document represents.
  - Why a document is distinct from the uploaded file.
  - Ownership (documents belong to exactly one workspace).
  - Separation of concerns between:
    - relational metadata
    - object storage (S3/MinIO)
    - searchable/vector representations.
  - Document lifecycle.
  - Recommended document status/state machine.
  - Failure behaviour.
  - Retry behaviour.
  - Deletion lifecycle.
  - Whether document versioning should be supported now or intentionally deferred.
  - Future extensibility for additional document sources (Google Drive, SharePoint, URLs, etc.).

  Architecture decisions already made

  - Workspaces are the tenancy boundary.
  - Documents are owned by workspaces, never individual users.
  - Users receive access through workspace membership.
  - Object storage is abstracted behind a provider boundary.
  - Search/indexing is independent from document persistence.
  - We favour durable state machines over multiple boolean flags.
  - We avoid premature complexity where a simpler architecture provides a stable foundation.

  Preferred lifecycle (feel free to improve naming if appropriate):

  UPLOADING
  ↓
  UPLOADED
  ↓
  QUEUED
  ↓
  PROCESSING
  ↓
  INDEXED

  Failure path:

  PROCESSING
  ↓
  FAILED

  Deletion:

  INDEXED
  ↓
  DELETING
  ↓
  DELETED

  Versioning should be explicitly discussed.

  My current preference is that every upload is initially treated as a new document and true document versioning is intentionally deferred until there is a clear product requirement.

  The ADR should explain trade-offs and rationale, not simply list decisions.

  Do not invent implementation details that belong in later stages.
