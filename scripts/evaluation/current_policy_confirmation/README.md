# Stop 3 confirmation boundary

No live authority, sealed inputs, credentials, provider prices or operational bindings are included here. USD 300 is only a proposed future ceiling.

`runner.py BINDING.json` verifies the frozen source/harness files, exact commit, mounted-runtime command and deadline before each item. It accepts the released shape exactly: `schema_version`, `package_id`, `note`, `evaluated_at_assumption`, `items[{id,utterance}]`. The binding's positive integer `expected_item_count` must equal the released count (six for smoke; the former confirmation used 68), preserving order without cohort/category labels. Grading assigns cohorts later.

The binding must supply: manifest path/hash; exact source commit and file hashes; mounted verification argv; actor/workspace/corpus/pinned-profile preflight expectation per item; existing product UI path and login identity; actual preflight/export argv; deadline; fresh output destination; maximum planning (including intrinsic calls), retrieval (including retries) and generation liability per item; pricing and reviewer-context hashes; and a separately approved authorisation bound to the binding hash. Never put login passwords in the binding/evidence; provide the browser password privately at execution. Source and deployed-runtime identities are different checks.

Real callbacks are connected: `preflight.php` invokes authorised scope construction and profile selection; `browser-check.mjs` submits once using the actual ChatWorkspace UI and existing idempotency API; `capture.php` reads that resulting run under actor/workspace scope. Browser completion and reload text/citation UUIDs are checked against saved output. A browser/capture uncertainty retains liability and halts, never resubmits. Exclusive start and authorisation-consumption markers prevent accidental replay. A fresh directory is required unless hash-bound `preparation_files` allow intact Phase A evidence and an empty capture directory. Unknown files/directories, item records or operational markers refuse execution without deletion.

## Stop 3a completion bound and capture

Preflight exports the existing backend `run_timeout_seconds`; the binding must match it. Immediately before the single Enter submission the browser records `submitted_at_ms`. The immutable completion bound is `min(submitted_at_ms + run_timeout_seconds * 1000 + 15000, overall_deadline_ms)`. The 15-second allowance is delivery/rendering only. The pure helper also accepts an authoritative backend deadline instead of submission-plus-duration, if one is supplied; this runner currently uses the duration because the API has no such deadline field. Setup is separately capped at 120 seconds and the remaining overall deadline. Polling, route remount, SSE reconnect and reload do not reset either bound. Expiry retains the most recent backend status, DOM, events and timing, and halts without resubmission.

Capture requires the correct completed run, exact canonical saved text, ordered citation UUIDs, cleared pending/progress state and the final announcement. Completion path is recorded as `sse`, `persisted_state` or `persisted_recovery`; receipt of SSE is not required when saved state establishes completion. Reload uses the same bound and exact comparisons, with no text normalisation. No harness code clears UI state. The controlled fixture alone may end SSE without a terminal event to exercise recovery; no live transport is changed.

Controlled asynchronous development fixtures use one-shot orchestration processes against disposable PostgreSQL and HTTP fakes, not production/evaluation queue workers. Delays are synthetic and are not provider-latency measurements. No sealed inputs or provider calls are needed for these checks.

Development manifests use the identical released schema and only synthetic controlled questions. The development record binds its parent commit plus changed-tree hashes explicitly. The final source freeze/local commit is published separately. Running these files does not authorise live spending or enable a client workspace.
